# AI Switch 产品优化建议

> 产品视角路线图与优先级（内部讨论稿）  
> 定位：本地「AI 开发工具的 Key 中枢」——管 Key、验健康、推配置，而不是再做一个聊天客户端。

## 核心价值主张

用户真正买账的只有 3 件事：

1. **一把 Key 改完，多工具立刻能用**
2. **坏 Key 别把工具搞挂**
3. **我能看懂现在系统在干什么**

凡是不服务这三点的功能，优先级都该往后排。

当前能力面已经很宽（供应商、健康、同步、后端引擎、统计、Profile、下游路由等），下一步更关键的是 **把主路径做稳、做懂、做少踩坑**，而不是继续堆功能。

## P0：信任与稳定性（不做就劝退）

### 1. 数据完整性与恢复

**问题**：`data.json` 损坏 → 供应商“全没了”，体验是灾难级。

**建议**：

- 损坏自动回退备份 + **UI 明确提示「已从备份恢复」**
- 导入 / 健康检测 / 用量写入前做 **schema 校验**
- 大文件场景：用量日志与主配置 **分库**（`data.json` 只存 vendors / settings）
- 「一键导出备份」入口放 Dashboard 显眼位置

### 2. 同步可预期

**问题**：未安装的后端仍可能被写配置；活跃供应商与 auth 不一致；Codex 被错误 Key 覆盖。

**建议**：

- 同步前 **Preview 必出结果**：将写入哪些文件 / 跳过哪些（未安装）
- 每个后端显示 **最后同步时间 + 结果摘要**（成功 / 跳过 / 失败原因）
- Codex 类「单活跃槽」后端：切换供应商时 **强制校验 Responses 流式可用**，失败则不切换
- 提供 **「仅同步到：OpenClaw / OpenCode / Codex」** 快捷预设

### 3. 后端状态三态可信

**问题**：未安装显示运行中 / 已运行显示停止，用户直接不信产品。

**建议**：

- 卡片文案统一：**未安装 | 已停止（可同步）| 运行中**
- 未安装：按钮灰掉 + tooltip「未检测到安装，不同步」
- 一键「打开安装说明 / 检测路径」
- 安装判定只认真实产品证据（CLI / 扩展），**不以本管理器写入的配置目录作为已安装依据**
- 运行中判定：守护进程 / 端口 / IDE app-server 等，避免把「仅有配置」当成运行中

## P1：主路径体验（日常使用频率最高）

### 4. 新手 3 分钟闭环

功能多时新人容易迷路。建议固定 **Onboarding 四步**：

1. 添加 1 个供应商 + 1 把 Key
2. 健康检测通过
3. 选择要同步的后端（只显示已安装）
4. 跳转「验证」：提示在 OpenCode / Codex 里发一句测试

完成前 Dashboard 只显示这四步，其它入口折叠。

### 5. 健康检测产品化

现在是「能检」，还不够「能决策」：

| 优化点 | 说明 |
|--------|------|
| 检测目标分层 | 连通性 / 模型列表 / **Codex 用 Responses 流式** / Chat Completions |
| 失败原因可读 | 401 / 429 / 额度 / SSL / 模型无通道 → 中文一句话 + 建议动作 |
| 自动策略 | 连续失败 N 次 → 自动禁用并不同步；恢复后提示重新启用 |
| 按用途标签 | 「适合 Codex」「适合 Claude Code」「仅聊天」 |

### 6. 批量导入「可撤销 + 不伤主数据」

**问题**：智能导入后数据异常，用户会怪导入。

**建议**：

- 导入永远是 **事务**：成功才 commit，失败整批回滚
- 导入后 Toast：**撤销本次导入**（undo 做成主路径）
- 预览页显示：新增 / 合并 / 跳过重复 的数量
- 重复 Key 策略可选：跳过 / 更新 / 并存

### 7. Key 生命周期管理

缺的不是「再多几个按钮」，而是运营感：

- 搜索 / 标签 / 备注（项目名、渠道、额度来源）
- 批量启用、禁用、删除、移动供应商
- 过期 / 额度预警（配合 429 / monthly limit）
- 「这把 Key 同步到了哪些后端」反向视图

## P1：差异化能力（容易形成口碑）

### 8. 后端「一键切换」标准化

Codex 已有 switch-provider，应推广为统一模型：

- OpenClaw 活跃模型 / 供应商
- OpenCode 默认 provider
- Claude Code 当前 env

统一 UX：`选择后端 → 选择供应商 / Key / 模型 → 验证 → 生效`  
验证失败 **不允许标记为成功**。

### 9. 「工作区 Profile」做成一等公民

多项目用户刚需：

- 工作 / 个人 / 实验 三套 Key 与同步策略
- 切换 Profile = 切换数据 + 可选自动推送后端
- 导出加密 Profile 分享给同事（密码保护）

### 10. 用量与成本：从“有图”到“能管”

统计有了，但决策闭环不够：

- 按供应商 / Key / 后端 看消耗
- 日 / 月预算阈值，超限自动禁用或只读告警
- 异常尖峰（某 Key 突然狂烧）通知

## P2：安全与分发（开源推广后会立刻被问）

### 11. 安全基线

- `access_token` 默认引导开启（至少局域网场景）
- 敏感字段 UI 默认脱敏，复制需二次确认
- 可选：系统钥匙串 / 本地加密存储 Key
- 审计日志：谁（本机用户）在何时改了 Key、推了同步

### 12. 安装与升级体验

- 首次启动检测：端口占用、权限、Node 版本（OpenClaw）
- 应用内「检查更新」+ changelog
- 一键诊断报告（便于 Issue：后端状态、最近错误、版本）

### 13. 文档与社区资产

开源获客后 Issue 会涌入：

- 3 分钟快速入门（图文）
- 「Codex 连不上」专项排障（Responses / env_key / web_search）
- 各后端「支持什么 / 不支持什么」对照表
- 适配器贡献指南（加一个后端要改哪些文件）

## 建议减负 / 克制的方向

| 慎重加 | 原因 |
|--------|------|
| 再堆 10 个边缘后端 | 安装检测与同步语义跟不上会反噬口碑 |
| 云端账号体系 | 与「本地 Key 中枢」定位冲突，合规成本高 |
| 做成全能 Agent | 会模糊价值，维护面爆炸 |
| 过度自动化切供应商 | 静默切换 = 用户失控感 |

**原则**：宁可少同步，不可错同步。

## 产品策略一句话

> **先成为「最让人放心的本地 Key 同步器」，再成为「最全能的 AI 工具控制台」。**

当前最该优化的不是功能数量，而是：

1. **别丢数据**
2. **别写错配置**
3. **状态别骗人**
4. **主路径 3 分钟跑通**
